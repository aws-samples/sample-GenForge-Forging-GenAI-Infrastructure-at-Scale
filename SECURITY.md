# Security Policy

## Reporting a Vulnerability

If you discover a potential security issue in this project we ask that you notify AWS/Amazon Security via our [vulnerability reporting page](http://aws.amazon.com/security/vulnerability-reporting/). Please do **not** create a public GitHub issue.

### Please Do Not

- **Do not** open a public GitHub issue for security vulnerabilities
- **Do not** disclose the vulnerability publicly until it has been addressed
- **Do not** exploit the vulnerability beyond what is necessary to demonstrate it

### What to Include

- Type of vulnerability
- Full paths of source file(s) related to the vulnerability
- Location of the affected source code (tag/branch/commit or direct URL)
- Step-by-step instructions to reproduce the issue
- Proof-of-concept or exploit code (if possible)
- Impact of the vulnerability, including how an attacker might exploit it

## Sample Code Disclaimer

GenForge is provided as **sample and educational code**. It is **not** intended for production use without additional security hardening, code review, and testing appropriate to your environment.

The generated infrastructure templates showcase reference patterns for provisioning GenAI workloads on AWS. Before deploying any generated code in a production environment, review the [Production Hardening Recommendations](#production-hardening-recommendations) below and adapt them to your organizational security requirements.

## Production Hardening Recommendations

Templates scaffolded by GenForge embed baseline security controls, but the following areas require additional attention before production deployment.

### Identity and Access Management (IAM)

- **Review every generated IAM role and policy.** Scaffolded roles are scoped to the minimum permissions expected for the reference workflow. If you extend a template, tighten policies to match your specific access patterns.
- **Avoid wildcard actions and resources.** The sample code intentionally avoids `service:*` grants. Do not reintroduce them.
- **Use permission boundaries.** For roles that will be assumed by human users or by CI workflows, attach a permission boundary that constrains the maximum privilege regardless of the attached policies.
- **Restrict `iam:PassRole`.** The generated Lambda and workflow roles include `iam:PassRole`. Scope it to specific role ARNs in production.
- **Restrict OIDC trust policies.** The default `GitHubActionsDeployRole` trust policy references `repo:<GITHUB_ORG>/*:ref:refs/heads/main`. Narrow the wildcard to specific repositories and branches.

### Encryption

- **At rest.** All S3 buckets, DynamoDB tables, and EBS volumes generated by templates use encryption at rest with either SSE-KMS or AWS-managed keys. Prefer customer-managed KMS keys for regulated workloads and enable automatic key rotation.
- **In transit.** All public-facing endpoints must use TLS. HTTPS listeners are configured on Application Load Balancers via the `certificateArn` scaffolder input. Do not disable HTTPS redirects.
- **Secrets.** Do not embed secrets in Git. Use AWS Secrets Manager or AWS Systems Manager Parameter Store, and grant task or Lambda roles read access only to the secrets they need.

### Network Isolation

- **VPC deployment.** Workloads that support VPC placement (RAG, MLflow, Lambda-based ingestion) should be deployed into private subnets.
- **VPC endpoints.** Prefer VPC endpoints (interface or gateway) for AWS service access. The QnA RAG template supports scoping OpenSearch Serverless to VPC endpoints only.
- **Security groups.** Review inbound rules on ALBs. In production, restrict source CIDRs or place the ALB behind AWS WAF, CloudFront, or a private connection.
- **Public endpoints.** Reconsider `internet-facing` load balancers for internal workloads. Use `internal` schemes where clients are inside the VPC.

### Container and Runtime Security

- **Non-root containers.** Container images generated by the EKS Strands Agents template run as a non-root user. Preserve this pattern for any custom images.
- **Image scanning.** Enable Amazon ECR scan-on-push and remediate Critical and High findings before promoting images.
- **Image signing.** Sign container images with AWS Signer or Cosign, and enforce signature verification at deploy time.
- **Read-only root filesystem.** Where possible, configure containers with a read-only root filesystem and explicit writable volumes.

### Logging, Monitoring, and Auditing

- **CloudTrail.** Ensure CloudTrail is enabled on the target account with log file validation and delivery to a centralized logging account.
- **VPC Flow Logs.** Enable VPC Flow Logs on VPCs deployed by the VPC template.
- **CloudWatch alarms.** Add alarms on Lambda errors, Fargate task failures, and unusual Bedrock invocation patterns.
- **GuardDuty and Security Hub.** Enable both services for continuous threat detection and compliance checks.

### Dependency and Supply Chain Security

- **Pin dependencies.** All Python `requirements.txt`, `package.json`, and CDK CLI versions in scaffolded workflows are pinned. Do not replace pinned versions with `latest`.
- **Dependency scanning.** Run `pip-audit`, `yarn audit`, and container image scanners as part of CI. Remediate Critical vulnerabilities before deployment.
- **GitHub Actions.** Third-party actions in generated workflows are pinned to major or exact versions. Prefer pinning to commit SHAs for maximum supply chain assurance.
- **CDK bootstrap.** The default CDK bootstrap policy is broad. Consider a custom bootstrap template with a scoped `cdk-exec-policy`.

### Data Protection and Privacy

- **Least-privilege data access.** Restrict which principals can read from S3 artifact buckets, DynamoDB experiment tables, and OpenSearch collections.
- **Data classification.** Tag resources holding sensitive data (`data-classification=confidential`, `pii=true`) and enforce policy through Service Control Policies or Attribute-Based Access Control.
- **Regional data residency.** Confirm the target AWS region complies with the data residency requirements applicable to your workload.

### Cost and Blast-Radius Controls

- **Environment-aware removal policies.** Production stacks use `RETAIN` for stateful resources. Do not switch to `DESTROY` for production.
- **Budgets and cost alarms.** Configure AWS Budgets with SNS notifications for the workloads deployed via GenForge.
- **Service Control Policies.** In multi-account setups, use SCPs to prevent accidental deployment of expensive resources (large SageMaker instances, unlimited Bedrock quotas) outside approved environments.

## Known Security Considerations

- **Sample code scope.** The templates demonstrate reference architectures. Additional hardening (custom KMS keys, WAF integration, private connectivity, fine-grained IAM) is expected before production use.
- **Bedrock model access.** Templates assume the required Bedrock foundation models have been enabled in the target account. Review model access grants for compliance with your data policies.
- **Local development mode.** In local development, Backstage uses a guest authentication provider. Never enable guest auth in a hosted environment.
- **Scaffolded repository visibility.** Templates create GitHub repositories with `private` visibility by default. Do not switch to `public` until security review is complete on the specific component.
